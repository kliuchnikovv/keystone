# Автоматизации: редактор и присутствие телефона

Документ отвечает на два вопроса:

1. **Как выглядит редактор автоматизаций на телефоне** — так, чтобы правило было
   видно целиком, а не списком полей.
2. **Откуда берётся «пришёл / ушёл»** — датчики присутствия и, главное, **телефон**.

Решения приняты 17.11.2026 (см. §6).

---

## 1. Что есть сегодня

**На хабе** (`core/`):

| Что | Файл | Что умеет |
|---|---|---|
| Правила | `rule_engine.hpp` | один триггер → предикат → одно действие; окно времени (`between`), одно доп. условие (`and`), cooldown |
| Расписания | `schedule_table.hpp` | время + дни/дата, солнце-относительные точки |
| Таймеры | `timer_table.hpp` | задержка в секундах |
| Сцены | `scene_table.hpp` | именованный набор до 8 настроек |

**В приложении** (`app/src/ui/AutomationForms.tsx`, `app/src/model/automation.ts`):
формы When / Then / More options (Between / Only while / Cooldown), расписания,
таймеры, сцены. Всё читается словами (`describeRule`).

**Чего нет:** нескольких действий в одном правиле, нескольких условий, «иначе»,
последовательности действий, правил на присутствие телефона.

## 2. Ограничения текущей модели (держим в уме расширение)

`core::Rule` — фиксированная структура:

```
trigger(entity, attr, op, operand) → action(entity, attr, value)
+ between(from, to) + and(entity, attr, op, operand) + cooldown_s
```

То есть: **один** триггер, **одно** действие, **одно** доп. условие.

Редактор проектируем так, будто эти ограничения скоро снимут:

- условия хранятся **списком**, а не одним полем;
- действие — **слот**, который сегодня один, но не «одно поле в форме»;
- в модели черновика — то же, что в протоколе, плюс поле `kind`, чтобы различать
  «условие» и «действие» без разбора структуры.

Тогда расширение до N действий — это изменение протокола и ядра, а **не** переписывание
форм.

## 3. Модель черновика правила

```ts
/** Что смотрим: устройство + атрибут + сравнение. */
export interface ConditionDraft {
  option: AttrOption | null;   // какое устройство и какой атрибут
  op: CmpOp;                   // 'any' | '==' | '!=' | '<' | '<=' | '>' | '>='
  value: string;               // как это набрано (в единицах человека)
}

/** Что делаем: устройство + атрибут + значение, либо сцена. */
export interface ActionDraft {
  option: AttrOption | null;
  value: string;
  scene?: string | null;
}

export interface RuleDraft {
  trigger: ConditionDraft | null;   // WHEN — обязателен
  conditions: ConditionDraft[];     // AND — сегодня максимум один
  action: ActionDraft | null;       // THEN — сегодня ровно один
  window: { from: string; to: string } | null;  // between
  cooldown_s: number | null;
}
```

`conditions` — массив, потому что это единственное место, где «список» не ломает
сегодняшний протокол: `rule.add` принимает один `and`, лишние условия отклоняются
с понятной ошибкой.

**Проверка на сохранении:** если `conditions.length > 1` — показать
«Пока хаб умеет одно дополнительное условие. Остальные — в Later».

## 4. Экран редактора

### 4.1 Блочная структура

Плоский список полей (`When` / `Then` / `More options` / `Between` / `Only while` /
`Cooldown`) на телефоне — это 6–7 экранов скролла, где человек теряет из виду, что
получилось. Заменяем на **блоки с чипами**: каждый блок — одна строка, каждый чип
тапается и открывает bottom sheet с выбором.

```
┌─ WHEN ────────────────────────────┐
│ [Датчик в коридоре] [Presence] [=] │
│ [Кто-то есть]                    │
└───────────────────────────────────┘
              ↓
┌─ AND (необязательно) ────────────┐
│ [+ добавить условие]             │
└───────────────────────────────────┘
              ↓
┌─ THEN ────────────────────────────┐
│ [Лампа в коридоре] [Яркость] [=]  │
│ [80 %]                            │
└───────────────────────────────────┘
```

Условия и окно времени — **внутри** блока WHEN (они про «когда»), действие — блок
THEN. Между блоками — стрелка ↓, она же показывает, что это цепочка.

### 4.2 Живой предпросмотр

Под блоками — одна строка словами, пересобираемая при каждом изменении:

> «Когда в Датчике в коридоре кто-то есть → лампа в коридоре, яркость 80 %»

Это главная вещь, которая даёт уверенность, что правило понято правильно.

### 4.3 Решение по компоновке

**Вертикальный столбик сверху вниз**, не горизонтальный flow. Горизонтальный flow
(n8n, Node-RED) на телефоне нечитаем: ширина экрана уходит на масштабирование, и
человек не видит правило целиком. Вертикальный столбик читается как текст.

Соединители между блоками — вертикальные, на всю ширину, с треугольником-стрелкой.
Когда появится flow-редактор с несколькими действиями, эта же разметка станет его
основой: блок действия — узел, «+» между блоками — вставка узла.

## 5. Присутствие: датчики и телефон

### 5.1 Датчики

Атрибут `hubproto::attr::kOccupied = 0x50` (bool, «someone is there») уже есть и
приходит с датчиков движения и с детекторов присутствия (IAS Zone). Хаб уже умеет
IAS Zone → `occupied`.

Формулировки в UI:

| Атрибут | Значение | Как читается |
|---|---|---|
| `occupied` | `true` | «Кто-то есть» |
| `occupied` | `false` | «Никого нет» |
| `contact` | `true` | «Закрыто» |
| `contact` | `false` | «Открыто» |

**Важная оговорка:** `occupied == false` означает «никого не видно», а не «ушёл».
Разница между «мимо прошёл» и «ушёл» из PIR-датчика не выводится.

**«Ушёл из комнаты» — отдельная фича** (`last_seen`): время последнего
`occupied == true`; условие «нет никого N минут» = `now - last_seen > N`. Требует
правки в `core` (новый атрибут + хранение) и нового вида сравнения. Записано в
[backlog.md](backlog.md).

### 5.2 Телефон

Телефон — **не** устройство на хабе: у него нет `entity_id`/`attr_id`, он не в
`EntityRegistry`. Значит правило на хабе не может иметь его триггером, если хаб
ничего о нём не знает.

**Решение: телефон — виртуальная сущность.** Хаб заводит для телефона сущность с
атрибутом «дома» (bool) — ровно как датчик движения. Правило ссылается на неё как
на обычное устройство. `RuleEngine` не меняется.

```
Rule {
  trigger_entity: <phone entity>,
  trigger_attr:   kHome,        // bool
  op: Eq, operand: true,
  action_entity: lamp, action_attr: brightness, action_value: 80
}
```

**Несколько телефонов — несколько сущностей.** Один человек = один телефон = одна
сущность со своим именем («Телефон Анны»). Правило ссылается на конкретный.

**Событие присутствия:** телефон сообщает хабу «я дома» / «я ушёл». Хаб обновляет
атрибут и **рассылает** его как обычный STATE — правило срабатывает тем же путём,
что и датчик.

#### Что нужно для этого

| Слой | Что |
|---|---|
| Протокол | `presence.report {phone, home}` — телефон шлёт хабу |
| Ядро | виртуальная сущность телефона + атрибут «дома»; реестр должен уметь её завести |
| Приложение | нативный модуль следит за присутствием и шлёт событие |
| Правила | ничего — работает общий механизм |

#### Почему телефон сообщает, а не хаб спрашивает

Вариант «хаб спрашивает телефон по polling» — проще, но хаб узнаёт о присутствии с
задержкой (а хаб может быть не в сети, телефон может быть вне зоны). Вариант
«телефон сообщает» — событийный, и работает через релей: телефон вне дома пишет
хабу через туннель.

**Проблема фоновой работы — главный риск этой фичи.** iOS убивает фоновые
приложения, Android с Doze — тоже. Отсюда решение: следить за присутствием должен
**нативный код** (вариант «б»), а не JS в фоне:

- iOS: `CLLocationManager` с `startMonitoring(for:)` на круговом регионе +
  `startMonitoringSignificantLocationChanges`; при входе/выходе — колбэк, который
  открывает WebSocket и отправляет `presence.report`.
- Android: `GeofencingClient` (Play Services) или `LocationManager` с геозоной; там же
  `BroadcastReceiver`.

Приложение при этом может быть закрыто — работает нативный код.

#### Как телефон определяет, что «дома»

| Способ | Точность | Батарея | Заметка |
|---|---|---|---|
| **Geofence** (круг вокруг дома) | хорошая | средняя | iOS/Android, ~100 м; система сама будит приложение |
| **Wi-Fi SSID** | хорошая | низкая | телефон видел сеть — «дома» |
| **BLE-маяк у двери** | отличная | низкая | нужно железо; план на будущее |
| **Ручная кнопка «я дома»** | абсолютная | ноль | страховка всегда доступна |

**Берём geofence + Wi-Fi SSID**, ручную кнопку оставляем как запасной путь.

#### Гистерезис и подтверждение

Geofence сам по себе даёт ложные срабатывания:

- вышли за хлебом на 5 минут → хаб решил, что ушли;
- подъехали к дому → сработало в 200 м → свет включился в машине.

**Лечится двумя правилами:**

1. **Гистерезис:** вход в радиус 60 м, выход из радиуса 150 м. Убирает дребезг на границе.
2. **Окно подтверждения:** «ушёл» = геозоны нет **N минут** (по умолчанию 5). Гасит
   короткие выходы.

Оба — на стороне телефона (в нативном модуле), хаб получает уже чистые «дома»/
«не дома».

#### Спорное: «дома» — это про дом или про конкретное устройство?

Домашняя геозона — это круг. Дом может быть Г-образным, двор — часть участка.
Радиус 100 м вокруг дома ловит соседний дом. Поэтому:

- геозона ставится **вручную** в приложении (карта + радиус), а не «по умолчанию»;
- у пользователя есть ручное переключение «я дома / я не дома» — оно всегда поверх.

## 6. Решения (17.11.2026)

| # | Решение |
|---|---|
| 1 | Одно действие на правило. Модель черновика — со списком условий и слотом действия, чтобы расширение не ломало формы. |
| 2 | Условия присутствия — от датчиков **и** от телефона. Телефон = виртуальная сущность на хабе. |
| 3 | Присутствие телефона определяет **нативный код** (вариант «б»), не JS в фоне: iOS `CLLocationManager` геозоны, Android `GeofencingClient`. |
| 4 | Каждый телефон — отдельная сущность со своим именем. |
| 5 | Источник условия привязан к триггеру: если выбрано «когда я не дома» — это телефон. Отдельного переключателя «источник» нет. |

## 7. Порядок работы

**Шаг 1 — редактор (фронт, ядро не трогаем).**

- `app/src/model/automation.ts`: `RuleDraft`, `ConditionDraft`, `ActionDraft`,
  `draftToSentence()`, `draftRequest()`.
- `app/src/ui/AutomationForms.tsx`: блочный `RuleFormView` с чипами и живым
  предпросмотром.
- Формулировки присутствия («Кто-то есть» / «Никого нет»).
- Тесты: `app/test/automation.test.ts`, `app/test/ui-automation.test.tsx`.

**Шаг 2 — присутствие телефона (ядро + протокол + нативный код).** ✅ сделано, кроме
проверки на железе.

- **Протокол**: `presence.report {name, home}` — телефон говорит, где его хозяин;
  `presence.list` — какие телефоны знает хаб; `presence.remove {entity}` — забыть.
  (`docs/app-protocol.md` §5.)
- **Ядро**: `core/presence.hpp` (новый) — таблица телефонов: entity id, имя, когда
  сообщал, что сообщал; **устаревание** (молчал дольше 15 минут → присутствие
  *неизвестно*, а не «не дома»); персистентность (NVS `presence`), чтобы правило,
  указывающее на телефон, переживало перезагрузку. Виртуальная сущность:
  `hubproto::DeviceType::Phone` (0x0B) + атрибут `hubproto::attr::kHome` (0x52).
  Значение уходит на шину **обычным STATE** — значит правило срабатывает ровно так же,
  как на датчик движения, и `RuleEngine` не меняется.
- **Реестр**: `EntityRegistry::declare_virtual()` — сущность, которой нет ни у одного
  чипа.
- **Matter**: телефон — **не** аксессуар (`core/matter_plan.hpp` отдаёт пустой план),
  в Apple Home его нет.
- **Приложение**: `app/src/model/presence.ts` (состояние и слова), `app/src/ui/PresenceCard.tsx`
  (карточка на вкладке Hub + ручное «я дома / я не дома»), `app/src/hooks/useGeofence.ts`
  (запуск геозоны), нативный модуль: iOS `KeystoneGeofence.swift`
  (`CLLocationManager`, регион + гистерезис + подтверждение), Android `GeofenceWatcher.kt`
  (`GeofencingClient` + `GeofenceBroadcastReceiver`).

**Шаг 3 — Later.**

- Несколько действий в правиле, «иначе», последовательности.
