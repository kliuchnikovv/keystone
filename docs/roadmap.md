# Роадмап — что мы хотим получить и как туда прийти

**Цель на ближайшие полгода: продукт/демо, который можно отдать другому человеку.**
Зафиксировано 29.10.2026.

**Обновление 29.10.2026:** релей поднят на удалённом сервере и работает — ESP-клиент на
хабе проверен end-to-end через публичный wss-эндпоинт (коммит `2d5be9e`). Значит
получателю демо не нужно быть в нашей сети: удалённый доступ уже рабочая часть
продукта. И одновременно релей становится тем, что мы отдаём наружу, — его безопасность
идёт в Track C: [relay-security.md](relay-security.md).

**Обновление 30.10.2026:** путь «телефон → релей → туннель → хаб» проверен на живом
релее (Railway) с настоящим токеном. По дороге закрыты две неисправности, обе на
сервере: буфер релея терял `<cid>:` у кадра, ждавшего хаба, и проверка `Origin`
отказывала origin самого релея (его шлёт RN-WebSocket на iOS). Приложение при этом
было корректным. Осталось: `RELAY_STATUS_TOKEN` на Railway (чтобы статус-страница
показывала адрес для приложения) и — главное для цели «отдать коробку» — способ
передать токен другому человеку (сейчас его знает только настроивший хаб).

Этот файл — **единственный источник правды о приоритетах**. Бэклоги по подсистемам
([brain](brain-backlog.md), [zigbee](zigbee-backlog.md), [matter](matter-backlog.md),
[cross-cutting](backlog.md)) описывают, *что ещё не сделано*; порядок и критерии
«готово» — здесь. Сводная таблица в [overview.md §3](overview.md#3-сводный-бэклог) —
срез на момент её написания, не источник.

## 1. Что означает цель

Человек получает коробку. У него нет ноутбука, нет USB-консоли, нет наших
инструкций. Он должен: **включить → хаб сам поднимает Wi-Fi → он добавляет хаб в
Apple Home → видит свои устройства → добавляет ещё одно → всё работает.**

Значит главный вопрос меняется с «что ещё умеет хаб» на «**может ли человек без
ноутбука открыть коробку и получить работающий дом**». Всё, что не в этом пути, —
в Later.

### 1.1 Что уже доказано на живом железе

| Что | Статус |
|---|---|
| Один Zigbee-устройство: IKEA INSPELNING (on/off + power_w + energy_wh) | ✅ join → declare → state → command → ack |
| Matter-мост: Apple Home комиссионит хаб по BLE+Thread, toggle доходит до плага | ✅ end-to-end |
| Хаб как Wi-Fi+SNTP+WebSocket-сервер, wss с пиннингом, mDNS | ✅ на живом хабе |
| Remote access: ESP relay-клиент хаба через публичный релей | ✅ коммит `2d5be9e` |
| Remote access: **телефон → релей → туннель → хаб**, с токеном | ✅ 30.10.2026, живой релей на Railway |
| Приложение: веб-бандл против mock-хаба и живого хаба | ✅ только веб |

### 1.2 Что написано, но **не проверено на железе**

Это и есть главный долг. Не фичи, а доверие.

- Zigbee: IAS Zone (контакт/движение/дым), Level, Color, Thermostat, Generic Switch,
  multi-endpoint, ZDO rejoin, retry back-off.
- Matter: зеркала всех типов выше (сделаны через `inject`, не на реальных устройствах).
- Setup по воздуху: виден ли `Keystone-XXXX`, отвечает ли 192.168.4.1:8443 по WPA2,
  `connectLearning` на Swift/Kotlin, весь телефонный флоу.
- Unpair на живом устройстве + удаление Matter-зеркала.
- thread-c6: `energy_wh` в прод-ране (фикс `ScopedChipStackLock` собран, не гонялся).
- Приложение: нативный модуль (`keystone-net`) ни разу не выполнялся на телефоне —
  через релей путь идёт штатным WebSocket (пин там не нужен), а вот **прямое**
  подключение к хабу с пиннингом на телефоне не проверено; iOS-сборка не дошла до
  `xcodebuild archive` (профиль подписи истёк 24.10.2026).

## 2. Два трека: демо не должно ждать приложения

Matter-путь — единственный, проверенный end-to-end на живом железе. Приложение —
самое рискованное (нативный модуль не выполнялся, подпись истекла). Если ждать оба,
демо сдвигается на «после починки подписи».

| | Трек A — золотой путь | Трек B — приложение |
|---|---|---|
| **Что доказывает** | Коробка работает: AP → Wi-Fi → устройство → Apple Home → toggle | Наше приложение — полноценный пульт |
| **Поверхность** | Apple Home | Keystone app (iOS/Android/web) |
| **Блокирует демо?** | **Да** | Нет |
| **Статус** | ~90 % написано, не проверено по воздуху | ~80 % написано, не выполнено на телефоне |

**Track C — доверие** (OTA-подпись, flash encryption, factory reset, recovery) идёт
параллельно и обязателен до того, как коробка уедет к другому человеку.

### Этап 1 — Золотой путь, Track A (главный по ценности)

- [ ] **Этикетка на коробку.** `scripts/make-label.sh` печатает её: setup code (пароль
      точки доступа — без него получатель не начнёт) и Matter code для Apple Home.
      Сейчас наклейки нет вообще.
- [ ] **Пройти процедуру по [docs/golden-path.md](golden-path.md)** — от «воткнули в
      розетку» до «работает в Apple Home», двумя вариантами (с консолью и без) и с
      таблицей симптомов.

- [ ] **Setup по воздуху, целиком:** AP `Keystone-XXXX` виден → WPA2 с кодом с
      этикетки → `wss://192.168.4.1:8443` отвечает → `connectLearning` на
      Swift/Kotlin → `wifi.scan` → `setup.apply` → хаб на сети → приложение видит
      хаб по mDNS.
- [ ] **Ловушка диапазона (2.4 ГГц).** ESP32-S3 — только 2.4 ГГц. Если у человека
      5 ГГц-only или band steering, он подключится к AP, увидит сеть в `wifi.scan`
      (роутеры часто вещают один SSID в обоих диапазонах) и хаб не зайдёт. Нужен
      явный отказ с человеческим текстом и подсказкой в приложении, а не «join failed».
- [ ] **Apple Home на чистом хабе:** новый fabric, QR из Matter setup code
      (`3497-0112-332`, уже показан в карточке «Apple Home bridge» на Hub-вкладке),
      устройства появляются в Home и рулятся.
- [ ] **Unpair без призрака:** устройство уходит с Zigbee → его endpoint исчезает и
      из Home (сценарий `Undeclare` → `app_bridge_remove_device`).
- [ ] **3–4 реальных типа устройств**, каждый полным циклом:
      join → declare → state → command → ack → Matter-зеркало → сценарий (правило
      или сцена). Порядок по ценности: датчик движения/контакта → диммируемая лампа →
      кнопка/пульт → термостат. Один тип — это демо «розетки», четыре — демо «хаба».
- [ ] **Каждое устройство — фикстура,** а не разовый прогон: пункт в lab-листе
      (join, что ждём, что проверяем), чтобы «проверено на железе» не зависело от
      памяти.
- [ ] **Воспроизводимость сборки:** `scripts/flash-all.sh` — три платы по порядку
      через один USB-хаб + готовый набор прошивок, чтобы демо не зависело от
      моей машины.

**Готово, когда:** чистый хаб + 4 типа устройств проходят сценарий от коробки до
Apple Home, и этот сценарий повторяется на другом человеке без участия разработчика.

- [ ] **Подпись OTA-образов.** Сейчас OTA-endpoint открыт: любой в LAN перепрошивает

- [ ] **Релей: секрет на хаб вместо глобального.** Сегодня один `RELAY_SECRET` на все

- [x] **Релей: TLS подтверждён, статус-страница закрыта, лимиты и rate limit на auth.**

      `Origin`, постоянного времени сравнение секрета. TLS на развёрнутом релее —
      Let's Encrypt (край Railway), HTTP → 301 → HTTPS.
- [x] **Честная документация о модели доверия.** Релей видит токен и трафик — если это
      «свой релей» получателя, так и написано, а не обещан шифротекст. Полный список

## 4. Сколько чипов нужно хабу и какие конфигурации поддерживаем

**Ответ: 3 чипа — это продукт. 2 — стенд. 1 — не хаб.**

| Чипов | Состав | Что умеет | Статус |
|---|---|---|---|
| 1 | только мозг (S3) | локальный API, без радио | **не хаб**, не поддерживаем |
| 2 | мозг (S3) + 1 C6 (Zigbee) | Zigbee-устройства, приложение, правила; **без** Apple Home | стенд, не SKU |
| 3 | мозг (S3) + C6 (Zigbee) + C6 (Matter) | полный хаб: Zigbee + Apple Home + приложение + удалённый доступ | **продукт** |
| 4 | + ESP32-CAM (рекордер) | запись событий на SD | не делаем — тот же журнал дешевле на LittleFS мозга |

Почему нельзя дешевле:

- **Мозг — это S3 (или больше).** На C6 мозгу не жить: 512 КБ RAM, 4 МБ флеш, а
  Zigbee-стек требует `zb_storage`, Matter — два слота по 1.92 МБ. Плюс к мозгу
  Wi-Fi + TLS + WebSocket-сервер.
- **Два радиочипа — потому что 802.15.4 один.** Zigbee и Thread/Matter не уживутся
  на одном 802.15.4: это разные фрейминги, а не флажок в прошивке. Значит Apple Home
  требует второго C6.
- **Один C6 не может быть «и Zigbee, и Matter»** — это разные протоколы на одном радио.

Что уже работает: **прошивка мозга не зависит от наличия второго C6.** Ничто не ждёт
chip 0x02 на старте (self-heal QUERY просто уходит в пустоту), а единственное место,
где нужны оба чипа, — отправка `Undeclare` на Matter-чип, и там проверка правильная.
Вариант «2 чипа» — это та же прошивка на другом железе.

**Рекомендация по железу:** одна плата с двумя посадочными местами под C6-модули, две
линии UART и линии `EN`+`BOOT` на оба (этап 3). Тогда lite-вариант — это
неприпаянный второй C6 и другая прошивка на оставшемся, а не второй продукт.

**Какие конфигурации поддерживаем: одну** — три чипа. Две — стенд. Второй SKU удваивает
матрицу прошивки и проверок, а выигрыш только в цене; ради этого достаточно стендовой
сборки, а не линейки.

Отдельно: SPEC §2.2 упоминает запасные S3 #2 и C6 #3..#5. Для продукта они лишние —
каждый лишний вариант прошивки умножает матрицу проверок.

## 5. Риски «чужого дома» (их нет в бэклогах)

| Риск | Где всплывёт | Митигация |
|---|---|---|
| Роутер только 5 ГГц / band steering | setup, join Wi-Fi | Явный отказ с текстом + подсказка в приложении (этап 1) |
| AP isolation / гостевой Wi-Fi в чужом роутере | телефон не достучится до хаба | Текст в README получателя + relay как обходной путь |
| Тест-DAC: «Uncertified Accessory» в Apple Home | комиссионинг | Решение в этапе 4 |
| Один общий токен на всех | любой, кто знает токен, рулит домом | Для одной семьи норма; на демо — отдельный токен на хаб |
| Токен приложения живёт только у того, кто настраивал хаб | получатель в чужом доме не может подключиться к хабу (ни напрямую, ни через релей) | Токен на наклейку/QR либо одноразовый код при первичной настройке (этап 1) |
| Wi-Fi пароль и TLS-ключ в NVS открытым текстом | доступ к флеш-памяти | Flash encryption (этап 3) |
| Устройство молча уходит с сети | дом не реагирует | ChipMonitor + реконсиляция уже есть; журнал событий (этап 3) |

## 6. Что сознательно не делаем

- **Разгрузка на C6** (локальный event-buffer, локальный rule fast-path, дебаунс на
  чипе): мозг не перегружен (~215 KB свободно), а инвариант «мозг рассуждает обо всём
  доме» дороже выигрыша в миллисекундах. Только если появится измеримая боль.
- **DSL правил (Berry/Lua)** — упрёмся в табличные правила.
- **Миграция мозга на P4/Linux** — инвариант держит, повода нет.
- **Recorder-CAM как sink** — LittleFS на brain дешевле и без второй платы.
- **Сертификация Matter, multi-fabric, per-user ACL** — не продукт.
- **Thread Border Router** — вне объёма.

## 7. ИИ-функции: где живёт ИИ

Релей — естественное место для ИИ: у него есть интернет, он всегда включён, и
приложение уже умеет с ним говорить. Но здесь развилка, которую надо решить
**до** того, как что-то писать:

> **Если ИИ работает на нашем релее — наш релей видит дом.** Это прямое
> противоречие модели B («релей не хранит пользовательскую информацию»): не
> хранение, но доступ. Значит выбор места ИИ определяет, возможна ли вообще
> модель B.

| Где живёт ИИ | Что видит оператор релея | Цена |
|---|---|---|
| **На телефоне** (модель на устройстве или облачный API, вызванный с телефона) | ничего | ИИ работает, пока открыто приложение |
| **На своём железе** (Pi в локальной сети, рядом с хабом) | ничего | полностью локально, нужен рантайм модели |
| **На нашем релее** | **всё состояние и вся история** | нужна модель B или явный отказ от неё |

**Решено 29.10.2026:** ИИ — **отдельный платный сервис**, который добавим позже, для
упрощения действий. Отсюда:

- **Релей остаётся слепым транспортом.** ИИ-сервис — отдельная программа, которая
  заходит в хаб как обычный клиент протокола через `/client/<hub-id>`. Ни строчки
  нового кода в релее для ИИ не нужно.
- **Платный тариф — это тариф, где мы видим дом.** Пользователь платит и получает
  ИИ, который читает его состояние и историю; это надо написать в условиях явно.
  Бесплатный тариф и свой релей остаются слепыми — модель B (E2E-канал) сохраняет
  силу именно там.
- **Что уже готово:** протокол отдаёт ИИ-сервису всё нужное — `welcome` + `snapshot`
  (частями по 4 КБ), запрос `history` (с `before`/`limit`/`entity`), `cmd` и `req`.
  Сервис пишется обычным клиентом протокола, **правки прошивки не нужны**. В
  `hello` уже есть необязательное поле `client` (до 32 символов).
- **Что добавить, когда дойдём (три мелочи):**
  1. `CmdSource::Ai = 9` (и `kCmdSourceMax = 9`) — чтобы в истории было видно
     «это сделал ИИ», а не «приложение».
  2. **Отзываемый второй ключ на хабе для ИИ-сервиса** — не пользовательский
     токен. Иначе отключить ИИ от дома можно только сменой токена, а это рвёт
     доступ самого приложения.
  3. Подписка и учёт — на стороне сервиса, не на хабе.

**Рекомендация:** ИИ — на стороне пользователя (телефон или его собственная
машина), релей остаётся транспортом. Это сохраняет принцип «локально прежде
всего» (SPEC §1) и не отменяет модель B. Если ИИ всё-таки нужен на нашем
релее — это решение «мы оператор, который видит ваш дом», и оно должно быть
написано в README крупным шрифтом.

Что ИИ может делать, опираясь на уже сделанное:

- **Разговор с домом.** «Выключи всё в гостиной» → команда через существующий
  `cmd`/`req`, а не новый путь управления.
- **«Что происходило сегодня?»** — журнал событий уже хранит источник каждой
  команды (`core::CmdSource`: консоль, приложение, правило, расписание, таймер,
  сцена, Matter, reconciler) — этого хватает для ответа «почему включился свет».
- **Разбор энергии** — `power_w`/`energy_wh` уже текут от хаба.
- **Правило по фразе** — через существующий `rule.add`: ИИ предлагает правило,
  человек видит и подтверждает.

**Инвариант:** ИИ — это интерфейс к существующему слою команд, а не второй
rule engine. Всё, что делает ИИ, идёт через `cmd`/`req` → диспетчер →
desired-state → reconciler → события. Тогда действия ИИ видны, отменяемы и не
расходятся с тем, что уже умеет хаб. ИИ не пишет правила в обход `rule.add` и не
меняет состояние напрямую.

**Порядок:** ИИ — после золотого пути (этап 1) и после того, как приложение
умеет показать и подтвердить действие. Первая версия: одно намерение
(«выключи X») → команда → подтверждение в приложении → результат.
