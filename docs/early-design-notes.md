# Полный бэкап чата — ESP32 Smart-Home Hub

Резюме всего обсуждения: проектирование ядра умного дома на C++/ESP-IDF поверх
нескольких ESP32-чипов. Ниже — главная цель, все решения в хронологии, все
технические артефакты (протокол, форматы, структура репо) в code-блоках,
упомянутые ссылки и нерешённые вопросы.

---

## 1. Главная тема / цель

Построить **локальный хаб умного дома** на C++ / ESP-IDF, работающий на
нескольких ESP32-чипах в одной коробке. Переносится ядро Home Assistant (шина
событий, реестр сущностей со стейт-машиной, движок правил) — **но не** экосистема
HA (тысячи интеграций, history DB, шаблонизатор, веб-UI).

Цель эволюционировала по ходу чата:
- старт: «ядро HA на C++ на ESP32» (для себя);
- финал: **хаб-заменитель** других хабов — человек покупает устройства и
  подключает к нашему хабу. Пока платформа «для себя», но с амбициями в продукт.

---

## 2. Ключевые решения и выводы (хронология)

### 2.1 Осуществимость ядра
- **Да, ядро реализуемо** на C++/ESP32: шина событий (FreeRTOS-очереди), реестр
  сущностей + стейт-машина (hash-map entity→state), движок правил
  (триггер/условие/действие).
- **Главный ограничитель — RAM**, не CPU. Фрагментация хипа — враг; жить на
  статических пулах/фиксированных аллокаторах, а не на вольном `std::string`.
- Чего не будет на ESP: 2000+ интеграций, history/recorder (максимум кольцевой
  буфер / SD), Jinja2-шаблонизатор (вместо — встраиваемый мини-язык **Berry** ~40 КБ
  или **Lua**).
- **Prior art к изучению: ESPHome** (C++ на ESP32, есть standalone-режим без HA) и
  **Tasmota** (C++ + движок правил + Berry).

### 2.2 Память и хранилище
- **microSD = storage, не RAM.** Помогает history/recorder, конфигу, логам — но не
  реестру/очередям (они в RAM).
- **ESP32-CAM имеет 4 МБ PSRAM** (стоит ради буферов камеры) — это бьёт прямо в
  узкое место по RAM. CAM по памяти ближе к S3+PSRAM, чем к «голому» ESP32.
- ESP32-CAM оговорки: мало GPIO (камера занимает), PSRAM медленнее SRAM и
  DMA-ограничена, нет USB-UART (прошивка через внешний FTDI).
- **Решение: CAM → «нода-recorder»** (PSRAM + SD-слот для истории).

### 2.3 Железо (инвентарь рос по ходу)
- ESP32-CAM (AI-Thinker): 4 МБ PSRAM, SD-слот, FTDI для прошивки.
- **ESP32-S3-Zero** (Waveshare): 512 КБ SRAM, 2 МБ PSRAM, 4 МБ флеша, USB-C native
  (прошивка по одному кабелю, зажать BOOT), 16+ свободных GPIO, RGB-LED.
- nRF24L01+ — проприетарный 2.4 ГГц трансивер (см. 2.13).
- Докуплены: **ESP32-C6 dev-боарды** (QIQIAZI 5-pack, USB-C + CH343, 512KB/320KB
  ROM/4MB Flash, €12.99 за 1 / €26.59 за 5 → взят 5-pack ради цены за штуку и
  запаса радио-чипов).

### 2.4 Брокер / шина — развилка
- Выделенный **ESP32-брокер** — самый слабый вариант: возвращает SPOF, встраиваемые
  брокеры (`sMQTTBroker`/`uMQTTBroker`) незрелые, нет персистентности retained без
  SD.
- Варианты: Mosquitto на внешнем железе (надёжно), ESP32-only (SPOF), ESP-NOW
  (без брокера, p2p).
- **Выбор: ESP-NOW broadcast как шина + CAM-логгер на SD.**

### 2.5 ESP-NOW — особенности
- **250 байт на сообщение** → компактный бинарный формат, не JSON.
- **Broadcast без ACK = лоссовая шина.** Решение: каждая нода **периодически
  ре-бродкастит полное состояние** (замена retained-сообщениям; идемпотентно,
  самозаживающе).
- **Общий канал с WiFi:** ESP-NOW обязан быть на канале WiFi-точки, если нода
  поднимает WiFi. Для старта — чистый ESP-NOW на фиксированном канале.
- **Шину сделать абстракцией** (`bus.publish/subscribe` поверх сменного
  транспорта) — ключевое решение, переживёт все переезды.

### 2.6 Надёжность доставки — ACK vs seq vs NAK
- **ACK через логгер — отклонено:** ложная уверенность («логгер услышал» ≠ «целевая
  нода услышала») + возвращает SPOF (ноды начинают зависеть от логгера).
- **Монотонный счётчик `seq` на продюсера — принят:** даёт детект потери (разрыв),
  дедуп (seq ≤ виденного), порядок.
- **Модель NAK/pull вместо ACK/push:** консьюмер видит разрыв → сам шлёт resync-запрос
  → продюсер отвечает полным состоянием. Инициатива у заинтересованного, трафик
  только при реальной потере, нет SPOF, нет ACK-имплозии.
- **Критичные адресные команды** (замок, котёл) → **ESP-NOW unicast** (канальный ACK
  встроен), а не app-level ACK поверх broadcast.

### 2.7 Ребут и версия состояния
- **Не восстанавливать seq после ребута.** «Запросить у сети» ломается при массовом
  обесточивании; «хранить в логгере» возвращает зависимость. Оба занижают seq →
  коллизии.
- **Решение: `boot_id` (epoch).** При ребуте seq сбрасывается в 0, меняется boot_id;
  версия состояния = пара `(boot_id, seq)`.
- Два способа boot_id: персистентный счётчик в NVS (строгий порядок, 1 запись на
  загрузку) vs **случайный boot-nonce в RAM** (`esp_random()`, ноль записей, сравнение
  «изменился ли»). **Выбран случайный boot-nonce.**
- **Версия события затвердела:** `(producer_id, boot_id, seq)`.

### 2.8 Расширения Matter/Zigbee = мосты = шлюзы
- Matter/Zigbee **не встраиваются** в ESP-NOW — подключаются с краю через нод-мосты.
  Любой мост = **SPOF для своего сегмента** (by design у Zigbee/Matter обязателен
  координатор/бордер-роутер).
- **ESP-NOW = native-слой без SPOF; всё внешнее = foreign-слои со шлюзами.**
- **Zigbee:** у S3/CAM нет радио 802.15.4 → нужен внешний координатор-донгл или
  чип **ESP32-C6/H2** (у них 802.15.4 + `esp-zigbee-sdk`).
- **Matter-over-WiFi:** S3 умеет (`esp-matter`), но конфликт каналов WiFi↔ESP-NOW;
  Matter тяжёлый (комиссионинг, сертификаты, fabric, IPv6).
- **Matter-over-Thread:** Thread = 802.15.4 (как Zigbee, другой стек) → снова C6/H2
  + Thread Border Router.

### 2.9 Прочие «не всё» для умного дома
- **Время:** без WiFi нет NTP, на платах нет RTC → «у дома нет часов». Варианты:
  внешний RTC (DS3231) на ноду-логгер + бродкаст времени как сущности, либо одна
  нода с WiFi ради NTP. **Решить рано.**
- **UI / поверхность управления** — на чистом ESP-NOW без WiFi веб-морды нет
  (позже решено через Matter-бридж наружу, см. 2.16).
- **Discovery / capability-модель** — нужен типизированный протокол объявления
  сущностей и их возможностей.
- **Кросс-нодовые автоматизации** — кто исполняет правило на две ноды.
- **OTA** — обычно по WiFi.
- **Безопасность** — ESP-NOW шифрование (PMK/LMK), лимит шифрованных пиров, подпись
  критичных команд.
- Несколько пунктов тянут в сторону «дать одной ноде WiFi» → **пограничная нода**
  (время + UI + OTA + внешние интеграции).

### 2.10 Соединение пинов разных ESP проводами
- **Да, законно.** Правила:
  - **Общая земля обязательна** (сигнал + GND минимум).
  - Все платы 3.3 В логика → соединяются **напрямую**, без level-shifter. CAM
    питается 5 В, но GPIO всё равно 3.3 В. **Никогда 5 В на GPIO ESP32.**
  - **Не соединять два выхода напрямую** (КЗ). Соединять через протокол:
    одиночная GPIO-линия (1 бит, wake-линия), UART (точка-точка, 2 платы),
    I2C (много плат, 2 провода + подтяжки), SPI (быстрее, 4+ провода).
  - Не вешать межплатные сигналы на **strapping-пины** (GPIO0/45/46). GPIO34–39 —
    только вход.
  - Прямой GPIO — **короткие дистанции** (одна коробка). Через дом — RS-485 или CAN,
    не сырой GPIO.
- **Вывод:** co-located ноды связывать проводом (UART/I2C) — детерминированный
  канал без потерь, ESP-NOW между ними не нужен. Гибрид: провод внутри кластеров,
  радио между кластерами. Абстракция шины это проглатывает (транспорт «wired»).
- Питание: земли связать; шины 3.3/5 В двух плат с собственными регуляторами между
  собой **не** соединять.

### 2.11 Отказ от ESP-NOW?
- Зависит от того, **помещаются ли все ноды в один физический кластер**:
  - всё в одной коробке → **ESP-NOW не нужен**, провод (UART/I2C/CAN);
  - распределены + проводная магистраль через дом → **CAN** (у ESP есть TWAI на
    чипе + внешний трансивер; аппаратные ACK/ретрансмит упрощают протокол) или
    **RS-485**;
  - распределены без кабеля → **ESP-NOW остаётся**.
- Выбор = новостройка/ремонт (можно тянуть кабель → CAN) vs retrofit (→ ESP-NOW).
- Не окончательно: CAN/RS-485/ESP-NOW — реализации одного транспортного интерфейса.

### 2.12 C3 для радио? — нет
- **ESP32-C3 = WiFi + BLE только, нет 802.15.4.** Zigbee/Thread не умеет.
- Чипы с 802.15.4: **C6** (WiFi6 + BLE + 802.15.4) и **H2** (BLE + 802.15.4, **без
  WiFi**).
- H2 не умеет ESP-NOW (нет WiFi-радио) → цепляется проводом. C6 умеет ESP-NOW.
- C3 годится под: **BLE-мост** (дешёвые BLE-датчики) или **WiFi-пограничник**.

### 2.13 nRF24L01
- Проприетарный (Enhanced ShockBurst), по SPI. **Не WiFi/BLE/802.15.4.** Zigbee/
  Thread/Matter **не умеет**, C6/H2 не заменяет, под приём покупных устройств
  **бесполезен**.
- Ниша: **транспорт для собственных DIY-нод**. Мост принимает nRF24-пакеты и
  объявляет их мозгу теми же `DECLARE`. Для ядра неотличим от Zigbee-устройства.
- Библиотеки: `RF24`, `RF24Network`, `RF24Mesh`.
- Для беспроводного end-to-end теста **нужно 2 модуля** (оба конца nRF24). С одним —
  только отладка драйвера/моста.

### 2.14 C6 — универсал
- WiFi 6 + BLE + 802.15.4 в одном чипе. Может: Zigbee-мост, сам на ESP-NOW (есть
  WiFi), WiFi-пограничник.
- **Коэкзистенция:** все радио делят одну 2.4 ГГц антенну (RF-коэкзистенция
  работает, но нагруженный режим). Часто C6 не перегружают — одна главная
  foreign-роль.
- **Два C6** → развести роли (Zigbee-координатор + WiFi-пограничник/Thread).

### 2.15 Переход к хабу (ключевой сдвиг)
- «Все платы ядра в одной коробке, приборы по дому без проводов» = **централизованный
  хаб**, а не распределёнка. Распределены **устройства**, не ноды; связь с ними —
  радио (Zigbee/BLE/Thread).
- **ESP-NOW между платами ядра больше не нужен** — провод в коробке. Весь антилосс-
  протокол (`seq`/NAK/`boot_id`/ре-бродкаст) — это была защита от радио **между
  нодами**; его больше нет. (Переезжает на новый слой: мозг↔радио-чип, см. протокол.)
- **SPOF = сама коробка** (принятый размен: простота ценой живучести; как HA/
  Zigbee2MQTT). Нужен UPS + watchdog.
- Несколько чипов оправданы теперь **разделением радио** (один чип = одна радио-роль),
  а не живучестью.
- **Кросс-нодовые правила упрощаются:** мозг видит весь реестр → правило исполняется
  локально в одном месте, без гонок.
- Остаётся и важнее: **абстракция шины** (теперь внутренняя шина хаба), реестр +
  стейт-машина + движок правил.

### 2.16 Matter — три роли
- **№1 Устройство** (прикидывается лампой наружу): ✅ легко, `esp-matter`.
- **№2 Бридж** (показывает пачку своих не-Matter устройств наружу): ✅ `esp-matter`.
  **Matter Bridge** — штатный тип устройства; решает проблему UI: Apple/Google/Alexa
  становятся UI бесплатно, локально. Живёт на WiFi-чипе-пограничнике (Matter-over-WiFi).
- **№3 Контроллер** (принимает и рулит чужими устройствами): ⚠️ тяжело на ESP.
  **Цель проекта = №3.**
- Outbound (№1/№2) — DIY-стратегия «не писать UI». Inbound (№3) — суть хаба-заменителя.
- Inbound-Thread обычно не нужен: покупные Matter-over-Thread устройства экосистема
  (Apple TV/HomePod со встроенным Thread BR) видит и так. Thread-inbound оправдан
  только при «полном суверенитете без чужих экосистем» (большая работа, свой Border
  Router).

### 2.17 Проблема роли контроллера = память, не CPU и не «нет кода»
- **CPU не проблема** (крипта аппаратно ускорена, комиссионинг разовый).
- **Код:** device/bridge SDK зрелый; controller-код в `connectedhomeip` **есть**, но
  урезанный, «для разработки», не продуктовый. Первопроходство.
- **RAM — главная стена:** пик комиссионинга (TLS-сессия) + живые сессии/подписки
  (линейно с числом устройств; лимиты `CHIP_IM_MAX_NUM_SUBSCRIPTIONS` и т.п. на ESP
  ставят низко).
- **Флеш/NVS:** fabric-состояние (сертификаты/ACL/node ID на **каждый** узел) растёт
  линейно; дефолтный NVS крошечный.
- **Одновременность стеков** (WiFi+Thread+mDNS+N сессий) — не масштабируется на
  FreeRTOS/сотнях КБ, деградирует обвалом.
- Проверка: **все реальные Matter-контроллеры на Linux-SoC с гигабайтами** (Apple TV,
  Nest Hub, SmartThings, HA Yellow). Ни одного на MCU.

### 2.18 Железо с большей памятью
- **ESP32-P4:** 16/32 МБ PSRAM (×4 к S3), RISC-V 2×400 МГц, 768 КБ SRAM. **Нет радио**
  → нужен чип-компаньон (C6/C5) по SDIO/SPI. **Не Linux-класс** — отодвигает стену
  контроллера, не сносит. Идеальный «толстый мозг» под наш паттерн.
- **SBC (когда до контроллера всерьёз):** Radxa Rock 5B+ (RK3588, до 32 ГБ RAM,
  NVMe, ~€265), Orange Pi 5 (4 ГБ ~€65), **x86 мини-ПК на N100** (Beelink/Minisforum/
  GMKtec, <$130, x86-совместимость, но нет GPIO и ~6 Вт). HA официально поддерживал
  ODROID N2+ — **снят с производства**; для новых сборок Pi 5 или N100.
- Предупреждение: **узкое место — софтверная экосистема платы, не спеки.** Брать то,
  у чего живой mainline-kernel/Armbian.

### 2.19 Оценка потолка по устройствам
- S3: узкое место — heap (~5–15 КБ рантайма на активно-подписанное устройство, ~300
  КБ полезного heap) → **низкие десятки** (~10–30).
- Fabric-состояние: ~2–4 КБ/устройство в NVS; с раздутым разделом 512 КБ–1 МБ → сотня-
  две на бумаге (÷~1.5 за NVS-оверхед). **Флеш не самая тесная стена.**
- **P4 с 32 МБ PSRAM:** heap в PSRAM → память перестаёт быть стеной; потолок
  сдвигается на **низкие сотни**; упрёшься уже в CPU event-loop / mDNS / reporting.
  Оговорка: PSRAM медленнее, DMA-ограничена — горячую крипту в SRAM, холодное
  состояние подписок в PSRAM.

### 2.20 Мультизадачность
- **Своя не нужна:** ESP-IDF = FreeRTOS (вытесняющая, 2 ядра, очереди). Переписывать —
  минус время, ноль выгоды.
- **Смена планировщика не создаёт память** — стена это RAM под состояние, не шедулер.
- Различать: планировщик (выигрыша нет) vs **модель конкурентности** (event-loop
  экономнее потока-на-соединение). Но `connectedhomeip` **уже event-loop** — efficient-
  путь пройден.
- **Реальный выигрыш «сделаю сам»:** не шедулер, а **своя компактная сериализация
  fabric-состояния** на littlefs/SD вместо дефолтного NVS-KVS (страничного, с
  оверхедом).

### 2.21 Чипы под Matter + Zigbee — считать радио, не чипы
- **До 3 независимых радио:** WiFi (Matter-over-WiFi + IP-backbone), 802.15.4-Zigbee,
  802.15.4-Thread.
- **Zigbee и Thread делят одно 802.15.4-радио, но режим выбирается при прошивке —
  одновременно только один.** Оба разом → два раздельных 802.15.4-радио.
- Коэкзистенция: на C6 WiFi и Thread делят RF-путь, не принимают одновременно (ок для
  низкотрафиковых). **ESP32-C5** (двухдиапазонный WiFi 2.4+5 ГГц + 802.15.4, 8 МБ
  PSRAM) уводит WiFi на 5 ГГц из толкучки — лечит коэкзистенцию.
- **Минимум (без Thread) — 2 чипа:** S3 (мозг + WiFi + Matter-over-WiFi) + 1 C6
  (Zigbee). Покрывает ~90 % Matter-мира (он в основном WiFi) + весь Zigbee.
- **Полный (с Thread) — 3 чипа:** S3 + H2 (Thread RCP, референс Espressif = S3+H2) +
  C6/H2 (Zigbee). Либо C6 как самодостаточный Thread BR (но WiFi обязателен — потерял
  WiFi, Thread-устройства отваливаются).
- **Совет: старт с 2-чиповой версии**, Thread третьим радио позже.

### 2.22 Что тестируется только на S3 + CAM
- **Всё, кроме 802.15.4.** В частности:
  - межчип-протокол + ядро целиком (CAM как радио-заглушка с фейковыми сущностями);
  - **Matter-over-WiFi в обе стороны** — в т.ч. **CAM как Matter-устройство + S3 как
    контроллер** → полный end-to-end тест роли №3 без покупки устройств (и видно, где
    RAM-потолок);
  - recorder на SD, BLE-сканер на S3, camera motion → событие, время (если дать WiFi).
- **Нельзя без докупки:** Zigbee-координатор, Thread/Matter-over-Thread (нет радио).

### 2.23 Минимальная докупка
- **Один ESP32-C6** — если брать одно. Уровни: 0 = ничего (Matter-over-WiFi + DIY
  только, без Zigbee); **1 = +1 C6 (Zigbee) — честный минимум**; 2 = +2 чипа (Zigbee +
  Thread).
- Брать **dev-борду** (USB на борту), не голый модуль.

### 2.24 План после приезда C6

## 3. Код / протокол / конфиги (артефакты)

> В чате не писался исполняемый код — проектировался **межчип-протокол** и собрана
> `SPEC.md`. Ниже все конкретные технические раскладки.

### 3.1 Версия события (эволюция, ESP-NOW эпоха)

```
Версия состояния = (producer_id, boot_id, seq)
  producer_id — кто продюсер
  boot_id     — случайный boot-nonce (esp_random()), новый при каждом старте,
                консьюмер сравнивает "изменился ли" → ресинк
  seq         — монотонный счётчик на продюсера: детект потери (разрыв),
                дедуп (seq ≤ виденного), порядок
```

### 3.2 Кадровый слой (Layer 1 — framing)

```
Кадр на проводе:
  [ COBS( HEADER || PAYLOAD || CRC16 ) ]  0x00

  COBS — Consistent Overhead Byte Stuffing: вычищает 0x00 из тела,
         0x00 = однозначный разделитель кадров, самосинхронизация после сбоя.
  CRC16 = CRC-16/CCITT-FALSE над (HEADER || PAYLOAD), ДО COBS.
  Приёмник: читать до 0x00 → COBS-decode → проверить CRC16 → битый кадр дропнуть.
```

### 3.3 Заголовок сообщения (Layer 2 — 8 байт, little-endian)

```
offset size field       meaning
0      1    version     версия протокола, старт 0x01
1      1    type        тип сообщения
2      1    chip_id     идентичность собеседника (0x00=мозг,
                        0x01..0xFE=радио-чипы, 0xFF=broadcast/unassigned)
3      1    boot_id     счётчик перезагрузок отправителя (NVS, ++ при старте)
4      2    seq         сопоставление запрос↔ответ (LE)
6      2    entity_id   субъект (LE; 0x0000 = про сам чип)

На проводе (в отличие от ESP-NOW): провод не лоссовый → seq НЕ про потери,
а про матчинг COMMAND↔CMD_ACK. boot_id — примитив ресинка: мозг видит смену →
сбрасывает сущности чипа и переспрашивает.
```

### 3.4 Типы сообщений

```
0x01 HELLO        chip→brain   "загрузился; chip_id, boot_id"
0x02 DECLARE      chip→brain   одна сущность + capability-дескриптор
0x03 DECLARE_END  chip→brain   "объявил всё"
0x10 STATE        chip→brain   сущность изменила атрибут(ы)
0x20 COMMAND      brain→chip   установить атрибут Y на сущности X
0x21 CMD_ACK      chip→brain   результат COMMAND seq=K (ok/fail/unreachable/unsupported)
0x30 QUERY        brain→chip   "(пере)объяви все сущности"
0x40 HEARTBEAT    both         liveness; отсутствие N интервалов = чип упал
```

### 3.5 Поток жизни

```
Boot / link-up:
  chip → HELLO(chip_id, boot_id)
  brain → QUERY
  chip → DECLARE (xN)
  chip → DECLARE_END
Runtime:
  chip → STATE                        (устройство изменилось)
  brain → COMMAND ; chip → CMD_ACK    (мозг рулит)
  both → HEARTBEAT                    (фон)
Resync:
  chip ребут → новый HELLO с инкрементнутым boot_id
  brain дропает сущности чипа, пере-QUERY   (самозаживание)

Критичные команды (замки/котлы): нет CMD_ACK в таймаут ⇒ чип завис ⇒
эскалация (ретрай → алерт). Некритичные STATE — без ACK, следующий отчёт вытеснит.
```

### 3.6 Форматы пейлоадов (LE)

```
HELLO:        (пусто — chip_id и boot_id в заголовке)

DECLARE:
  uint16 entity_id
  uint8  device_type
  uint8  attr_count
  Attribute[attr_count]:
    uint8 attr_id
    uint8 value_type
    uint8 flags        # bit0 readable, bit1 writable, bit2 reportable

DECLARE_END:  (пусто)

STATE:
  uint16 entity_id
  uint8  attr_count
  ValueEntry[attr_count]:
    uint8 attr_id
    <байты значения по value_type>

COMMAND:
  uint16 entity_id
  uint8  attr_id
  <байты значения по value_type>

CMD_ACK:
  uint8  status        # 0=ok 1=fail 2=unreachable 3=unsupported

HEARTBEAT:    (пусто)
```

### 3.7 Capability-модель — device_type ↔ Matter (форма Matter-кластеров)

```
device_type | value | Matter Device Type              | атрибуты (attr_id)
------------|-------|---------------------------------|-----------------------------------
light       | 0x01  | On/Off + Dimmable + Color Light | on_off(0x01), brightness(0x02),
            |       |                                 | color_xy(0x03), color_temp(0x04)
sensor      | 0x02  | Sensor                          | temperature(0x10), humidity(0x11),
            |       |                                 | illuminance(0x12), battery(0x1F)
switch      | 0x03  | On/Off Plug-in Unit             | on_off(0x01)
cover       | 0x04  | Window Covering                 | position(0x20), state(0x21)
lock        | 0x05  | Door Lock                       | locked(0x30)
climate     | 0x06  | Thermostat                      | setpoint(0x40), mode(0x41),
            |       |                                 | current_temp(0x10)
occupancy   | 0x07  | Occupancy Sensor                | occupied(0x50)
contact     | 0x08  | Contact Sensor                  | contact(0x51)
button      | 0x09  | Generic Switch                  | event(0x60)

Один дескриптор кормит внутренний реестр И Matter-бридж наружу.
Zigbee-лампа и DIY-реле с одним дескриптором неотличимы для мозга.
```

### 3.8 value_type enum

```
0x01 bool      (1 байт: 0/1)
0x02 uint8     (1 байт)
0x03 int16     (2 байта LE)      # напр. температура в 0.1°C
0x04 uint16    (2 байта LE)
0x05 float32   (4 байта IEEE754) # избегать на горячих путях; лучше scaled int
0x06 xy_color  (4 байта: uint16 x, uint16 y)
0x07 enum8     (1 байт)
```

### 3.10 Фазы сборки (порядок из SPEC.md)

```
Phase 0 — Scaffold: репо, ESP-IDF v5.1+, хостовая сборка libhubproto/core, CI,
          blink RGB-LED на C6 и S3.
Phase 1 — Framing (host-only): COBS, CRC16-CCITT, header codec, (de)serialization,
          полные юнит-тесты. Без железа.
Phase 2 — UART link-up: UartTransport за Bus на S3 и C6 (TX↔RX крест + общий GND),
          HELLO + HEARTBEAT.
Phase 3 — Registry + declaration: C6 объявляет фейковые light/switch; QUERY→DECLARE→
          DECLARE_END; заполнение EntityRegistry.
Phase 4 — State + commands + rules: STATE вверх; COMMAND/CMD_ACK вниз; минимальный
          RuleEngine end-to-end.
Phase 5 — Resync: boot_id в NVS; ребут C6 → мозг детектит смену, пере-QUERY.
Phase 6 — Zigbee: esp-zigbee-sdk координатор на C6; реальное устройство; транслятор
          Zigbee-атрибут → DECLARE/STATE.
Phase 7 — Recorder: CAM пассивно пишет STATE на SD с таймстемпами + аннотации
          (смена boot_id, разрывы).
Phase 8 — Matter-over-WiFi bridge (outbound): esp-matter на мозге; сущности реестра
          наружу как Matter-аксессуары. Dev/test сертификаты.

MVP = Phases 0–6.
```

### 3.11 Проводка S3 ↔ CAM / C6 (UART)

```
UART point-to-point:  TX одной платы → RX другой (крест-накрест) + общий GND.
Full-duplex, без адресации на линии, без арбитража, изоляция отказов.
Не вешать на strapping-пины. chip_id держать в заголовке (топологонезависимость).

S3 имеет ~3 аппаратных UART-контроллера (один часто под консоль) — звезда
point-to-point тянется на 3-4 чипа; дальше нужна адресуемая шина (SPI + chip-select).
Быстрым чипам (плотный поток отчётов) — SPI вместо UART на 115200.
```
