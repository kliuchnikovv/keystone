## 1. Зачем и почему сейчас

Сегодня человек, прежде чем создать автоматизацию, должен выбрать один из четырёх типов — **Scenes / Schedules / Timers / Rules** — то есть перевести своё желание на внутренний словарь хаба *раньше*, чем сформулировал само желание. Автор продукта сам не чувствует разницы между типами — значит новичок не почувствует тем более. Это главный барьер «непонятно и не интуитивно».

Разница между тремя из четырёх типов — чисто техническая: это **разные ответы на вопрос «Когда»**, приклеенные к одному и тому же «сделать». Поэтому их можно свести к одной рамке **«Когда ___, сделать ___»** и убрать выбор типа из головы пользователя.

**Почему именно сейчас, до ассистента.** Позже появится свой ассистент (NL → автоматизация, уровень 2). Если ручной путь и ассистент сходятся в **одном черновике автоматизации**, ассистент не рисует свой экран, а кладёт готовый черновик в тот же конструктор, где человек его дочитывает и правит. Ручной путь — это «ассистент, которым работаете вы сами». Поэтому форму черновика надо довести сейчас, бесплатно закладывая точку схождения.

## 2. Цели, не-цели, анти-цели

**Цели.**
- Один вход «создать автоматизацию» без выбора типа заранее.
- Человек формулирует намерение, а система сама решает, правило это, расписание или таймер.
- Вход через **примеры** (готовые сценарии словами), дальше — **живая фраза-конструктор** с подставленными пропусками (выбор потока C → B).
- Список автоматизаций читается единообразно: «Когда X, сделать Y», независимо от того, чем это было внутри.
- Черновик автоматизации — единая структура, пригодная и для будущего ассистента.

**Не-цели (в этой работе).**
- Менять ядро/прошивку/протокол. Остаёмся на `rule.add` / `schedule.add` / `timer.add` как есть.
- Несколько действий в правиле, «иначе», последовательности (остаются в Later, см. [docs/automations.md](../../automations.md) §7).
- Присутствие телефона как триггер — механизм уже сделан отдельно; здесь он просто ещё один «датчик» среди триггеров-устройств.
- Переименование/алиасы автоматизаций.

**Анти-цели (это считать провалом, даже если «работает»).**
- Пользователь снова должен знать слова «rule/schedule/timer», чтобы что-то создать.
- Пустой экран-конструктор как первый кадр создания (страх чистого листа — то, что мы убираем).
- Конструктор, который обещает то, чего хаб не умеет (например условие на расписании) и падает на сохранении.

## 3. Ограничения

1. **Ядро не трогаем.** Каждый «Когда → сделать» должен лечь ровно на один из трёх существующих вызовов:
   - «Когда **устройство** что-то делает» → `rule.add` (триггер `when`, действие `then`, плюс `and` / `between` / `cooldown_s`).
   - «Когда **наступит время** (повтор по дням)» → `schedule.add` (`time` + `days`).
   - «Когда **наступит дата** (один раз)» → `schedule.add` (`time` + `date`).
   - «Когда **пройдёт время**» → `timer.add` (`delay_s`).
   - «Сделать»: `entity`+`action`/`value` **или** `scene` — все три вызова уже принимают сцену.
2. **Доп. условия и окно времени есть только у правил.** `schedule.add` / `timer.add` не принимают `and`/`between`. Значит набор «ещё опций» зависит от вида триггера (см. §5.4). Это не недоделка, а честное отражение возможностей хаба.
3. **Снимок умещается в кадр 4 КБ** (ограничение протокола) — на объём этой работы не влияет, но список и так уже разбит снапшотом.
4. **Единицы человека.** Значения вводятся как сегодня (`parseInput`/`SCALES`): яркость в %, температура в °C. Переиспользуем без изменений.
5. **Scenes остаются отдельно.** Сцена — это переиспользуемый блок «сделать», не «когда→что». Отдельная вкладка/раздел.

## 4. Рассмотренные подходы

Что было решено по ходу обсуждения (развилки уже закрыты пользователем):

- **Модель.** A — оставить четыре типа, умнее развести вход. **B — свести расписания+правила+таймеры к «Когда → сделать», Scenes отдельно.** → Выбрано **B**: одна мысль вместо выбора из четырёх слов, и это ровно то, как потом автоматизацию опишет ассистент.
- **Вход в создание.** Три варианта (макет `Поток создания автоматизации`):
  - A — пошаговый мастер (один вопрос на экран);
  - B — фраза-конструктор (весь экран — одна фраза с тапаемыми пропусками);
  - C — от примера (список готовых сценариев словами, + «с чистого листа»).
  → Выбрано **C → B**: примеры снимают страх пустого экрана (главное для «интуитивно») и ведут в фразу-конструктор с заполненными пропусками; «с чистого листа» открывает пустую фразу. Фраза ближе всего к языку будущего ассистента.

Отвергнутые как самостоятельные решения: чистый мастер A (слишком много тапов для повторного использования) и «умный разводящий вход» над четырьмя типами (не убирает словарь, только прячет его на шаг).

## 5. Как это устроено

### 5.1 Единый черновик автоматизации

Новая модель в `app/src/model/automation.ts`, рядом с существующими (их не удаляем — переиспользуем кусками):

```ts
export type TriggerKind = 'device' | 'timeOfDay' | 'date' | 'delay';

export interface AutomationDraft {
  kind: TriggerKind;

  // kind === 'device'  → обычное правило
  trigger: ConditionDraft | null;      // переиспользуем существующий тип
  conditions: ConditionDraft[];        // «только пока …» (хаб хранит одно)
  window: { from: string; to: string } | null;  // «только между …»
  cooldown_s: number | null;

  // kind === 'timeOfDay' | 'date'
  time: string;                        // "22:00" | "sunset+30"
  days: Days;                          // для 'timeOfDay'
  date: string | null;                 // "YYYY-MM-DD" для 'date'

  // kind === 'delay'
  minutes: string;                     // как набрано

  // общий «сделать» для всех видов
  action: ActionDraft | null;          // устройство или сцена
}
```

`ConditionDraft` / `ActionDraft` / `AttrOption` / `parseInput` / `SCALES` — уже есть, берём как есть.

### 5.2 Черновик → запрос (маршрутизация к трём вызовам)

Одна функция вместо трёх разрозненных мест:

```ts
export function automationRequest(d: AutomationDraft):
  Parsed<{ op: 'rule.add' | 'schedule.add' | 'timer.add'; args: Record<string, unknown> }>;
```

- `kind === 'device'` → собрать как сегодняшний `draftRequest` (уже написан), `op: 'rule.add'`.
- `kind === 'timeOfDay'` → `scheduleRequest({ time, days, entity|scene, action })` (уже написан), `op: 'schedule.add'`.
- `kind === 'date'` → `scheduleRequest({ time, date, … })`, `op: 'schedule.add'`.
- `kind === 'delay'` → `timerRequest({ minutes, entity|scene, action })` (уже написан), `op: 'timer.add'`.

«Сделать» (устройство/сцена) конвертируется в аргументы одинаково для всех видов — выносим в общий помощник `actionArgs(action)`.

### 5.3 Черновик → фраза (живой предпросмотр для всех видов)

```ts
export function automationToSentence(d: AutomationDraft): string;
```

Фраза строится по виду триггера, «сделать» — общий хвост:
- device: `Когда <датчик> <значение> → <действие>` (переиспуем логику `draftToSentence`, включая формулировки присутствия «Кто-то есть / Никого нет»).
- timeOfDay: `Каждый день в 22:00 → <действие>` / `По будням в 07:30 …` / `За 30 мин до заката …`.
- date: `Один раз, 20 окт 2026 в 19:00 → <действие>`.
- delay: `Через 10 минут → <действие>`.

Эта фраза — главный элемент уверенности: человек видит целиком то, что получится.

### 5.4 Экран-конструктор (B)

Один экран. Сверху — ключевые слова и тапаемые пропуски (слоты), снизу — живая фраза и «Сохранить».

```
КОГДА
[ выбрать, что запустит ▾ ]        ← тап открывает лист «вид триггера»

(после выбора вида — слоты под этот вид)

СДЕЛАТЬ
[ выбрать, что произойдёт ▾ ]      ← устройство или сцена

Ещё опции ▾                        ← состав зависит от вида (см. ниже)

┌ ПОЛУЧИТСЯ ───────────────────┐
│ <живая фраза>                 │
└───────────────────────────────┘
[ Отмена ]            [ Сохранить ]
```

**Лист «что запустит»** — четыре больших выбора (иконка + слово + подпись): «Устройство что-то делает», «Наступит время», «Наступит дата (один раз)», «Пройдёт время». Это единственное место, где виды названы, и названы человеческими словами, не «rule/schedule/timer».

**Слоты под каждый вид** (после выбора):
- device: `[устройство ▾] [сравнение ▾] [значение]` — ровно сегодняшний `ConditionBlock`.
- timeOfDay: `[время ▾ (HH:MM / закат±)] [дни ▾ (каждый день/будни/выходные/свои)]`.
- date: `[дата ▾] [время ▾]`.
- delay: `[через … минут]`.

**«Ещё опции» — адаптивно по виду** (ограничение §3.2):
- device: «только пока <условие>», «только между <временами>», «не чаще чем раз в <сек>».
- timeOfDay/date/delay: ничего (у них нет `and`/`between` в ядре). Кнопку «Ещё опции» для этих видов не показываем вовсе — не дразним тем, чего нет.

### 5.5 Вход через примеры (C)

Экран «Что автоматизировать?» — список готовых сценариев словами + «С чистого листа». Выбор примера создаёт `AutomationDraft` с предзаполненными полями и открывает конструктор (B); незаполненные слоты подсвечены как пропуски.

Предлагаемый стартовый набор (это **мой выбор**, прошу глянуть и поправить состав/формулировки):

| Пример | Вид | Что предзаполнено | Что просит дозаполнить |
|---|---|---|---|
| 🌙 Выключить что-то на ночь | timeOfDay | 23:00, каждый день, действие = off | устройство |
| 🚶 Включить свет, когда прихожу | device | триггер = presence «Кто-то есть», действие = on | датчик и лампа |
| ⏱️ Выключить через какое-то время | delay | действие = off | устройство и минуты |
| 📈 Среагировать на датчик | device | — | триггер и действие |
| 🎬 Включить сцену по времени | timeOfDay | каждый день, действие = сцена | время и сцена |
| ✎ С чистого листа | — (спросит вид) | ничего | всё |

Примеры — чистая проекция: каждый отдаёт частичный `AutomationDraft`. Данные (`PRESET_AUTOMATIONS`) — таблица, покрытая тестами; никакой логики в UI.

**Важно про предзаполнение.** Пример заполняет только поля, которые **не привязаны к конкретному устройству этого дома**: вид триггера (`kind`), время/дни, сравнение и значение-намёк (op/value для присутствия), сторона действия (on/off). Сам выбор устройства (`AttrOption`) пример **не** несёт — устройство человек подставляет в пропуск, потому что до открытия конструктора неизвестно, какие датчики/лампы есть. Поэтому в `ConditionDraft`/`ActionDraft` из пресета `option` остаётся `null`, а слот подсвечен как пропуск.

### 5.6 Слитый список «Автоматизации» (+ Scenes отдельно)

[AutomationsScreen.tsx](../../../app/src/ui/AutomationsScreen.tsx) сегодня: четыре вкладки. Становится **два раздела**:

- **Автоматизации** — склейка `home.rules` + `home.schedules` + `home.timers`, строки рисуем **существующими** `describeRule` / `describeSchedule` / `describeTimer` как есть (правило читается «Когда …, …», расписание — «22:00 · Off plug1 / каждый день», таймер — обратный отсчёт). Единая рамка «Когда → сделать» — про *создание* и про то, что всё лежит в одном разделе, а не про переписывание формулировок каждой строки: описания не трогаем. Разовые (таймер; дата-один-раз) и так читаются отдельно (отсчёт / «Once, …»). Удаление — в соответствующий вызов (`rule.del` / `schedule.del` / `timer.cancel`); источник строки помним в объединённой модели строки списка (ключ `('rule'|'sched'|'timer', index)`).
- **Scenes** — как сейчас, отдельно (список, Apply, Edit, Add scene).

Единый «+ Создать автоматизацию» ведёт в C → B. У сцен остаётся свой «Add scene» (сцена создаётся из текущего состояния устройств — другой поток, не трогаем).

Порядок в списке: по виду не сортируем; показываем как есть снапшотом (разделить разовые/повторяющиеся можно подзаголовком, но это полировка — решает строитель).

## 6. Формулировки (копирайт)

- Виды триггера называются действиями пользователя, не типами: «Устройство что-то делает», «Наступит время», «Наступит дата», «Пройдёт время».
- Присутствие — существующие формулировки (`presenceValueText`): «Кто-то есть / Никого нет», «Дома / Не дома», «Закрыто / Открыто».
- Разовость видна в списке словами: «сработает один раз» / обратный отсчёт против «каждый день».
- Ошибки — как сегодня, из `*Request`-функций (они уже дают человеку понятный текст).

## 7. Тесты

Чистые функции — хост-тестируемы (vitest), как всё в `automation.ts`:
- `automationRequest`: каждый из четырёх видов → правильный `op` и аргументы; «сделать устройство» и «сделать сцену» для каждого вида; невалидные значения дают понятную ошибку; `kind: 'device'` с `conditions.length > 1` отклоняется.
- `automationToSentence`: фраза для каждого вида, полупустой черновик, присутствие, закат-относительное время, дата.
- `PRESET_AUTOMATIONS`: каждый пример даёт валидный частичный черновик; «с чистого листа» пуст.
- UI (react-native-web в jsdom): выбор вида открывает нужные слоты; «Ещё опции» нет для time/date/delay; живая фраза обновляется; сохранение зовёт правильный `op`; пример предзаполняет слоты.

Цель — не уронить текущие 491 vitest; добавить ~20–30.

## 10. Калибровочные решения, принятые мной (прошу проверить при чтении)

- **Состав примеров** (§5.5) — предложен шесть штук; состав и формулировки открыты к правке.
- **Нет имён/алиасов** у автоматизаций: идентичность — сама фраза. (casanomi даёт алиасы; у нас это Later.)
- **«Ещё опции» скрыты** для триггеров время/дата/задержка, потому что ядро не хранит там `and`/`between`.
- **Scenes не входят** в единый конструктор как «вид триггера» — остаются отдельным разделом и доступны как «сделать».
- **Старые формы** `RuleEditor`/`ScheduleForm`/`TimerForm` заменяются единым конструктором; их request-функции (`draftRequest`/`scheduleRequest`/`timerRequest`) **остаются** как внутренности `automationRequest`.
