# Matter — протокол проверки на живом железе

**Аудитория:** тот, у кого в руках лампа и выключатель.
**Что покрывает:** всё, что нельзя закрыть автотестами, — реальный интервью устройства, реальные жесты кнопки, реальные разрывы связи.
**Что НЕ покрывает:** запуск окружения — он в [running-locally.md](running-locally.md), режим B.

## Зачем это отдельно от тестов

Юнит-тесты проверяют наши таблицы и наши конверсии. Они не могут проверить то, что приходит **от устройства**: заполнит ли лампа `BasicInformation`, объявит ли `DeviceTypeList`, долетят ли события кнопки. Всё это зависит от прошивки конкретного вендора, и единственный способ узнать — включить.

Один пункт в этом документе помечен ⚠️ — он с высокой вероятностью не заработает с первого раза, и это ожидаемо. Читай его причину до, а не после.

## 0. Что понадобится

| Что | Зачем |
|---|---|
| Лампа (IKEA WARMBLIXT или любая Matter-лампа) | блоки A, C, D |
| Выключатель/пульт с физическими кнопками | блок B |
| Thread Border Router в сети | если устройства на Thread |
| Mac в той же Wi-Fi, без VPN | mDNS должен ходить |

Устройства **уже добавлены в Apple Home** (или другую экосистему) — мы подключаемся вторым админом.

### Собрать свежее

Обязательно: sidecar запускается из `dist/`, а не из исходников. Забыть пересборку — самый частый способ потратить час на отладку старого кода.

```bash
cd sidecars/matter-server && npm install && npm run build && cd ../..
go build -o bin/keystone ./cmd/keystone
```

### Проверить, что не запущена старая копия

Два keystone на одном порту — реальная ловушка: один слушает IPv4, другой IPv6, а `localhost` резолвится в `::1`, и запросы уходят не в тот процесс.

```bash
lsof -nP -iTCP:7777 -sTCP:LISTEN; lsof -nP -iTCP:5580 -sTCP:LISTEN
```

Должно быть по одной строке на порт. Если больше — прибей лишние до начала.

### Запуск

Три терминала (подробности — running-locally.md, режим B):

```bash
cd sidecars/matter-server && node dist/index.js
```
```bash
./bin/keystone -matter-sidecar ws://localhost:5580
```
```bash
cd apps/web && yarn dev
```

Логи sidecar'а — JSON вперемешку с логами matter.js. Дальше по тексту команды вида `grep 'что-то' sidecar.log` подразумевают, что ты перенаправил вывод в файл: `node dist/index.js | tee sidecar.log`.

## Блок A — лампа

### A1. Подключение и стадии

**Шаги.** В Apple Home: долгий тап на лампе → Настройки → «Turn on Pairing Mode» → появится 11-значный код. В UI keystone: «+» → Apple Home → код → Подключить.

**Ожидаемо.** Стадии сменяются **по мере реальной работы**, а не по таймеру: `Ищем устройство → Защищённый канал → Проверяем и настраиваем → Подключаем к сети → Читаем возможности → Готово`.

**Как понять, что стадии настоящие.** Они идут неравномерно: «Проверяем и настраиваем» обычно самый долгий кусок, а «Защищённый канал» проскакивает быстро. Ровные интервалы по 4 и 15 секунд означали бы, что мы смотрим на старые эвристические таймеры.

**В логах keystone:**
```
matter node commissioned   nodeId=... fabric=1
device commissioned        name=... type=light
```

**Провал.** Ошибка на стадии `attesting` — устройство не прошло проверку сертификата (бывает у dev-прошивок). Ошибка `timeout` — окно пейринга закрылось, открой заново, оно живёт ~60 секунд.

### A2. Имя, производитель, тип

Это проверка того, что мы читаем `BasicInformation` и `Descriptor.DeviceTypeList`.

```bash
curl -s localhost:7777/devices | jq '.devices[] | {Name, Manufacturer, Model, Type}'
```

**Ожидаемо:** `Type: "light"`, а `Name` — то, как лампа называется у тебя в Apple Home (мы предпочитаем `NodeLabel`). Если пользовательского имени нет — «IKEA WARMBLIXT» из вендорских полей.

**Провал и что он значит:**

| Симптом | Причина |
|---|---|
| `Type: "sensor"` или `"switch"` | `DeviceTypeList` пустой → эндпоинт не проинтервьюирован. Смотри A3. |
| `Name: "Matter device 3"` | `BasicInformation` не прочитан — та же причина. |
| `Manufacturer` пустой, но тип верный | Вендор не заполнил поле. Не наша проблема. |

### A3. Начальное состояние без единого действия

Ключевой пункт: keystone должен знать состояние лампы **сразу**, не дожидаясь, пока её кто-то переключит.

**Шаги.** Выключи лампу в Apple Home. Перезапусти keystone (sidecar не трогай). Открой UI.

**Ожидаемо.** Лампа сразу показана выключенной, яркость и температура заполнены.

**В логах sidecar'а:**
```
client resubscribed with snapshot   sinceSeq=0 ... reason="no position"
matter state snapshot published     nodeId=... attributes=N
```
`attributes=0` означает, что снапшот пустой — состояние не прочитано, копай в сторону интервью эндпоинтов.

### A4. Управление

По одному, проверяя и UI, и саму лампу глазами:

```bash
ID=$(curl -s localhost:7777/devices | jq -r '.devices[] | select(.Type=="light") | .ID')

curl -s -X POST localhost:7777/devices/$ID/actions -d '{"feature":"onoff","action":"turn_on"}'
curl -s -X POST localhost:7777/devices/$ID/state   -d '{"feature":"brightness","key":"level","value":30}'
curl -s -X POST localhost:7777/devices/$ID/state   -d '{"feature":"color_temp","key":"kelvin","value":2700}'
```

Если лампа цветная:
```bash
curl -s -X POST localhost:7777/devices/$ID/actions \
  -d '{"feature":"color","action":"set","params":{"hue":120,"saturation":100}}'
```

**Ожидаемо.** Лампа физически реагирует на каждую команду. 2700K — заметно тёплый, 6500K — холодный. Hue 120 — зелёный.

**Почему это важно проверить именно лампой, а не логами.** Яркость, температура и цвет в Matter — read-only атрибуты: их меняют командами (`MoveToLevel`, `MoveToColorTemperature`, `MoveToHue`). Запись атрибута проходит без ошибки и **ничего не делает** — вызов вернёт `{"ok":true}`, а лампа не шелохнётся. Поэтому здесь смотрим глазами на лампу, а не на код ответа.

**Провал.** `no binding for feature=color` — лампа не объявила `ColorControl`, значит она не цветная. Ошибка `unsupported` — команда есть в нашей таблице, но не у этого устройства. `{"ok":true}` без реакции лампы — значит команда ушла как запись атрибута; смотри в лог sidecar'а, там будет `Invoke » ...` или `Write » ...`.

### A5. Реалтайм из Apple Home ← **главный пункт**

Ради этого делался StateStream.

**Шаги.** Оставь UI keystone открытым. Переключи лампу **в Apple Home** (не в keystone).

**Ожидаемо.** UI обновляется меньше чем за секунду, без перезагрузки.

**В логах keystone** (уровень debug): `state changed ... origin=device_report`.

**Провал — и это самый важный сигнал во всём документе.** Если UI не реагирует, проверь по порядку:

1. В логе sidecar'а есть `matter state stream failed` или `... ended unexpectedly`? Значит стрим падает — смотри текст ошибки.
2. Есть `matter peer had autoSubscribe off — enabled it`? Значит подписка была выключена, мы её включили — **перезапусти sidecar и проверь снова**.
3. Ничего из этого нет, но и событий нет → подписка не установилась. Это тот случай, ради которого писался супервизор: sidecar выглядит здоровым и молчит.

### A6. Плавное изменение

Покрути яркость в Apple Home ползунком туда-сюда несколько секунд.

**Ожидаемо.** UI следует за изменением. Возможен лаг — matter.js объединяет частые обновления (~250 мс), это нормально.

**На что смотреть.** В логе keystone не должно быть россыпи `matter subscriber slow, dropping event`. Одна-две строки при резком движении — терпимо, поток — значит потребитель не успевает.

## Блок B — выключатель

Сначала пойми, что у тебя в руках, — от этого зависит, какой раздел твой:

```bash
curl -s localhost:7777/devices | jq '.devices[] | {Name, Type, Features: [.Features[].Key]}'
```

- Фича **`onoff`** → это управляемый выключатель (реле). Раздел B1.
- Фича **`button`** → это пульт/кнопка, которая только шлёт события. Раздел B2.

### B1. Выключатель с реле

Проверяется ровно как лампа: A4 (команда `turn_on`/`turn_off`) и A5 (переключение физической клавишей отражается в UI).

### B2. Кнопка и жесты ⚠️

**Почему помечено.** Нажатие в Matter — это **событие**, а не атрибут. Мы подписываемся на документированный путь (`ChangeNotificationService`), но в matter.js событие peer'а проходит через `ClientEventEmitter`, который отдаёт его дальше только если у эндпоинта заполнен `behaviors.supported` — тот самый реестр, который у peer'ов оказывался пустым, когда мы чинили чтение кластеров. Проверить это без физической кнопки было нечем. **Если этот пункт провалится — это ожидаемая находка, а не сюрприз.**

**Шаги.** Открой UI (список устройств виден). Нажми кнопку на устройстве: одиночно, затем удержание, затем дважды подряд.

**Ожидаемо:**

| Жест | Плитка | Экран устройства |
|---|---|---|
| Одиночное | вспышка + «Нажатие» | «Кнопка нажата», кольцо расходится |
| Удержание | «Удержание» | «Долгое нажатие» |
| Двойное | «Двойное» | «Двойное нажатие» |

Подпись держится ~4 секунды и гаснет.

**Как проверить сырой поток, минуя UI:**
```bash
curl -N localhost:7777/stream | grep --line-buffered '"type":"event"'
```
Жми кнопку — должны идти строки с `"Name":"button_pressed"` и т.п.

**Если событий нет — диагностика по слоям, сверху вниз:**

1. **Sidecar получает?** `grep 'matter event' sidecar.log`. Строка `matter event path unavailable` означает, что мы не смогли подписаться вовсе.
2. **Sidecar отправляет?** Подключись к нему напрямую и жми кнопку:
   ```bash
   npx wscat -c ws://localhost:5580
   > {"id":"1","method":"subscribe","params":{}}
   ```
   Ждём кадры `{"event":"deviceEvent",...}`.
3. **Событий нет и там** → упирается в ограничение matter.js, описанное выше. Зафиксируй: модель кнопки, версию прошивки, и что именно видно (или не видно) в логах — это вход для следующей итерации.

Атрибут `CurrentPosition` при этом может меняться и без событий — если в `/stream` идут `"type":"state"` с `feature":"button"`, значит связь с кнопкой есть, а теряются именно события. Это ценная деталь, запиши её.

## Блок C — устойчивость

Здесь ломаем связь намеренно. Лампа должна остаться управляемой после каждого пункта.

### C1. Sidecar умер и вернулся

**Шаги.** Убей sidecar (Ctrl-C). Подожди 10 секунд. Запусти снова.

**Ожидаемо в логах keystone:**
```
matter sidecar connection lost — reconnecting
adapter backend unreachable — device state may be stale
matter adapter connected after retry
matter adapter resubscribed   since=... replayed=... snapshot=true
adapter backend reachable
```

**Проверь после.** Переключи лампу в Apple Home — UI должен снова реагировать. Это проверка того, что после реконнекта восстановилась не только связь, но и подписка.

**Провал.** Нет строки `connected after retry` → адаптер не пытается переподключиться, всё остальное бессмысленно.

### C2. Реплей пропущенного

**Шаги.** Убей sidecar. Пока он лежит, **переключи лампу в Apple Home 2–3 раза**. Подними sidecar.

**Ожидаемо.** UI показывает актуальное (последнее) состояние лампы. В логах keystone:
```
matter sidecar restarted — resetting event sequence   ours=... theirs=...
matter adapter resubscribed  snapshot=true
```
Здесь именно `snapshot=true`: sidecar перезапустился, его счётчик обнулился, дырку реплеем не закрыть, поэтому приезжает полное состояние. Это правильное поведение.

**Провал.** UI показывает состояние **до** разрыва и не обновляется дальше — значит счётчик не сбросился и все новые события считаются дубликатами.

### C3. Обрыв без закрытия (heartbeat)

Проверяет случай «кабель выдернули»: TCP-соединение висит полуоткрытым.

**Шаги.** Отключи Wi-Fi на Mac на 40 секунд, включи обратно. (Sidecar и keystone на одной машине, так что сокет между ними уцелеет — этот тест честнее делать, разнеся их по двум машинам. Если такой возможности нет, пункт можно пропустить, отметив это в отчёте.)

**Ожидаемо:** `matter ws heartbeat failed — forcing reconnect`, затем реконнект как в C1.

### C4. Корректное завершение

**Шаги.** Останови sidecar через `kill -TERM`.

**Ожидаемо:** `shutting down` → процесс завершается за считанные секунды. Строка `shutdown step timed out, continuing` допустима — это и есть страховка от зависания.

**Провал.** Процесс висит дольше 15 секунд.

## Блок D — ошибки и обнаружение

### D1. Понятные ошибки

```bash
curl -s -X POST localhost:7777/devices/commission \
  -d '{"transport":"matter","payload":"00000000000","name":"Нет такого"}'
```

**Ожидаемо.** Поток стадий заканчивается ошибкой, а в UI (если проверяешь через интерфейс) — человеческий текст, а не Go-ошибка с обёртками. Сырой текст спрятан под «Подробности».

Заведомо неверный формат кода:
```bash
curl -s -X POST localhost:7777/devices/commission -d '{"transport":"matter","payload":"12345","name":"x"}'
```
Ожидаемо примерно такое:

```json
{"stage":"discovering","message":"поиск устройства"}
{"stage":"error","message":"... setup code must be an 11- or 21-digit ... (bad_request)"}
```

Первый кадр `discovering` keystone отдаёт всегда, ещё до обращения к адаптеру, — это не признак того, что пейринг начался. Важно другое: сразу за ним идёт ошибка, а не череда стадий, и в тексте есть `bad_request`.

### D2. Поиск устройств в режиме пейринга

**Шаги.** Переведи лампу в режим пейринга (Apple Home → Turn on Pairing Mode) и **не** вводи код.

```bash
curl -N "localhost:7777/discover?transport=matter&timeout=15s"
```

**Ожидаемо.** Строка NDJSON с `ref`, `discriminator` и, если вендор его объявил, `type`. То же самое в UI на экране «Ищем устройства».

**Важно.** Найти — не значит подключить: passcode в анонсе не передаётся, код всё равно нужен. Пункт проверяет, что список наполняется.

**Провал.** Пусто → mDNS не доходит. Проверь, что Mac не на VPN и не на гостевой сети.

### D3. QR-код

Если на коробке есть `MT:...`:
```bash
curl -s -X POST localhost:7777/devices/commission \
  -d '{"transport":"matter","payload":"MT:XXXXXXXXXXXXXXXX","name":"Лампа по QR"}'
```
Ожидаемо: подключение проходит так же, как по цифровому коду.

### D4. Удаление

```bash
curl -s -X DELETE localhost:7777/devices/$ID
```
Ожидаемо: `{"ok":true}`, устройство исчезло из `/devices` и из UI. Если в ответе есть `adapter_warning` — устройство удалено у нас, но не ответило само (например, уже офлайн). Это допустимо, но запиши.

## Форма отчёта

Заполни и приложи к результату — по каждому пункту достаточно одного слова и, если провал, куска лога.

```
Оборудование:   лампа ______________  выключатель ______________
Экосистема:     Apple Home / Google Home / другое
Border Router:  ______________

A1 подключение и стадии    [ ok / fail ]
A2 имя, тип                [ ok / fail ]   Type=______  Name=______
A3 начальное состояние     [ ok / fail ]   attributes=____
A4 управление              [ ok / fail ]   что не сработало: ______
A5 реалтайм из Home  ★     [ ok / fail ]
A6 плавное изменение       [ ok / fail ]   dropping event: да/нет

B  тип устройства: onoff / button
B1 реле                    [ ok / fail / n/a ]
B2 жесты кнопки       ⚠️   [ ok / fail / n/a ]   события в /stream: да/нет
                                                 state с feature=button: да/нет

C1 реконнект               [ ok / fail ]
C2 реплей после рестарта   [ ok / fail ]
C3 heartbeat               [ ok / fail / пропущено ]
C4 завершение              [ ok / fail ]

D1 ошибки                  [ ok / fail ]
D2 поиск                   [ ok / fail ]   найдено устройств: ____
D3 QR                      [ ok / fail / n/a ]
D4 удаление                [ ok / fail ]
```

**Приоритет разбора, если провалов несколько:** A5 → A3 → C1 → всё остальное. Без A5 весь смысл интеграции теряется; без A3 состояние приходится «расшевеливать» руками; без C1 система живёт до первого сбоя.

## Подключение без чужой экосистемы

Всё выше подключало устройство **вторым админом** — код брался из Apple Home. Устройство из коробки подключается напрямую, кодом с наклейки, и Apple Home при этом не участвует. Но зависит от того, как устройство попадает в сеть:

| Устройство | Прямое подключение |
|---|---|
| Ethernet или уже в IP-сети | работает: скан увидит его по mDNS |
| Wi-Fi, из коробки | нужен BLE + Wi-Fi креды (блок «Устройство ещё не подключено к Wi-Fi?» на экране кода) |
| Thread, из коробки | нужен BLE + operational dataset от Border Router |

**BLE включается флагом:**

```bash
KEYSTONE_MATTER_BLE=true node dist/index.js
```

**На macOS это не работает.** Система убивает процесс, как только он трогает Bluetooth: у бинарника `node` нет ключа `NSBluetoothAlwaysUsageDescription` в Info.plist, и TCC шлёт SIGKILL — не ошибку, которую можно перехватить. Выглядит как беспричинное исчезновение процесса. Sidecar предупреждает об этом при старте. Для BLE нужен Linux (Raspberry Pi из режима C).

Проверить Wi-Fi-путь без BLE нельзя: устройство из коробки физически недостижимо, пока не окажется в сети.

## Известные ограничения — не баги

- **Живое видео с камер** не работает и не проверяется: Matter переносит только сигнализацию, сам поток идёт мимо. Снапшот и PTZ реализованы, но без камеры Matter 1.4 не проверены.
- **Многодевайсные QR** отклоняются осознанно.
- **BLE на macOS** невозможен из-за TCC (см. выше) — это ограничение платформы, а не наш баг.
- **Thread из коробки** требует operational dataset; Apple его наружу не отдаёт, нужен свой Border Router.
- **Производитель в списке найденных** не показывается: в анонсе есть только числовой vendor ID, справочника имён у нас нет.
- **Устройство из нашей же фабрики** может попасть в результаты поиска, если оно в multi-admin режиме.
